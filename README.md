# control-tower

Claude Code mod providing a control tower dashboard for Claude Code sessions.
The mod lives in `control-tower/`.

## Development

Always develop against the working copy, never against the installed copy:

```sh
claude --plugin-dir ./control-tower
```

## Checks

Run from the repository root:

```sh
claude plugin validate --strict control-tower
scripts/check-calls.sh control-tower
claude plugin test control-tower
```

`scripts/check-calls.sh` fails when the mod calls `$` outside
`fs`, `process`, `clock`, `ui`, `tool`, `state`, `env` and `session`.

### `scripts/check-calls.sh <mod-dir>`

`claude plugin validate` reports the `$` calls of each module but does not
refuse any noun, hence this guard. It reads `claude plugin validate --json`
(requires `jq`) and exits with:

- `0` when every `$.<noun>` call is allowed, or when the mod calls nothing on `$`;
- `1` with the forbidden calls listed on stdout (e.g. `$.http.fetch`);
- `1` when `validate` fails (missing directory, invalid mod): stderr gets
  `validate failed: <mod-dir>` followed by validate's error messages, one per
  line; stdout stays empty;
- `2` without exactly one argument (usage on stderr).

Its own test, which builds throwaway mods in `$TMPDIR` and removes them on exit:

```sh
scripts/check-calls.test.sh
```

## Layout

- `control-tower/.claude-plugin/plugin.json`: manifest (`--strict` requires `author`);
  `types` points to `./types/index.d.ts`; declares the `branchPattern` option
  (see [Branch resolution](#branch-resolution)) and the `testPattern` option
  (see [Automatic transitions](#automatic-transitions)).
- `control-tower/types/index.d.ts`: state contract (see [Issue store](#issue-store)).
- `control-tower/hooks/hooks.json`: declares the hook module `./register.ts`.
- `control-tower/hooks/register.ts`: registers `session.start` (registers the
  [`set_issue_step` tool](#set_issue_step-tool), then passes the event through),
  the `tool.call` hook that answers that tool, the `tool.call` hook on `Bash`
  that observes commands (see [Automatic transitions](#automatic-transitions)),
  and the `classic.SessionStart` hook that reloads the project's records (see
  [`reloadIssues`](#reloadissues-cwd)).
- `control-tower/hooks/register.test.ts`: run by `claude plugin test`.
- `control-tower/hooks/bash-observer.test.ts`: tests of the `Bash` observer
  through the hook, with a fake engine answering its `$` calls.
- `control-tower/hooks/issue-store.ts`: issue store (`saveIssue`, `loadIssue`,
  `reloadIssues`), used by the `set_issue_step` and `classic.SessionStart` hooks.
- `control-tower/hooks/issue-store.test.ts`: unit tests of the store with a
  hand-written fake `$` (the `$` given to plugin tests exposes neither `fs`,
  `process`, `env`, `state` nor `clock`).
- `control-tower/hooks/issue-resolver.ts`: issue resolution from the branch name
  (`resolveIssue`), used by the `set_issue_step` hook.
- `control-tower/hooks/issue-resolver.test.ts`: unit tests of the resolver with
  a hand-written fake `$`.
- `control-tower/hooks/issue-step.ts`: pure rules of `set_issue_step`
  (`invalidRequest`, `applyStep`, `STEPS`, `REQUESTED_STEPS`, `NOTE_MAX_LENGTH`);
  makes no `$` call.
- `control-tower/hooks/auto-step.ts`: pure rules of the automatic transitions
  (`autoStep`); makes no `$` call.
- `control-tower/hooks/auto-step.test.ts`: unit tests of these rules.
- `control-tower/.claude-plugin/types/`: types generated by the engine, git-ignored.
- `control-tower/tsconfig.json`: generated by the engine in `--plugin-dir`
  sessions, git-ignored.

## Issue store

Each tracked issue is one JSON file, the source of truth, outside any worktree:

```
$HOME/.claude/control-tower/<project>/<issue>.json
```

- `<project>` is the basename of the main worktree: the first `worktree <path>`
  line of `git worktree list --porcelain`, run in the record's `worktree`.
- `HOME` is read through `$.env.get("HOME")`; unset or empty is a failure.

### Record

`IssueRecord`, declared in `control-tower/types/index.d.ts`:

| Field | Type |
|-------|------|
| `issue` | `number` |
| `title` | `string \| null` |
| `step` | `spec`, `tests-ecrits`, `tests-valides`, `vert`, `refacto`, `doc`, `mr`, `ci`, `termine` |
| `blockedReason` | `string \| null` |
| `branch` | `string` |
| `worktree` | absolute path |
| `history` | `{ step, at (ISO 8601), source: 'claude' \| 'auto' \| 'manuel', note: string \| null }[]` |
| `updatedAt` | ISO 8601 UTC, set by the store |

"Blocked" is not a step: an issue is blocked when `blockedReason` is not null,
and `step` is kept. Unblocking sets `blockedReason` back to null.

The store does not check transitions nor append to `history`: the caller passes
the complete record.

### `saveIssue($, record)`

1. Sets `updatedAt` from `$.clock.now()`.
2. Writes the record (JSON, 2-space indent) with `$.fs.write` to
   `<issue>.json.tmp-<random UUID>` in the same directory, then moves it onto
   `<issue>.json` with `mv` (`$.fs` has no rename nor delete). Saves of
   different issues never share a temporary file. `mv` (and the `rm -f` below)
   run in the store directory, never in the session cwd, which may be a
   removed worktree.
3. Only after a successful `mv`, mirrors the full record in `$.state` under
   `{ plugin: "control-tower", key: "issues", id: "<issue>" }`.
4. Adds the issue number to `control-tower.issueIds` (see
   [Session reload](#session-reload)) when it is not there yet, keeping the list
   sorted, and returns `true`.

It never rejects. On any failure (git, `HOME` unset, write, `mv`, or any
rejected `$` call) it logs one line to the transcript and returns `false`, leaving
`$.state` untouched; a failed `mv` also removes the temporary file (`rm -f`):

```
control-tower: save failed <project>/<issue>: <message>
```

`<project>` is replaced by the worktree path when git fails. The message is the
process `stderr` (trailing newline trimmed) or the error message.

A rejected `$.state` call while adding to `issueIds` also logs `save failed` and
returns `false`, the file and the `issues` mirror being already written; the
next [reload](#session-reload) corrects `issueIds`.

### `loadIssue($, worktree, issue)`

Returns the parsed record, `null`, or `'unreadable'`. It never rejects and never
touches `$.state`.

- missing file: `null`, nothing logged;
- invalid JSON, git failure, `HOME` unset or any other error: `'unreadable'` and
  `control-tower: read failed <project>/<issue>: <message>` (worktree path
  instead of `<project>` when git fails).

The content is only `JSON.parse`d; its shape is not checked.

### Session reload

At every `classic.SessionStart`, whatever its source (`startup`, `resume`,
`clear`, `compact`, `fork`), the mod reloads in `$.state` the records of the
session's project, so the session sees the issues as they are on disk. Other
projects are never loaded: issue numbers are not unique across projects.

State keys (contract in `control-tower/types/index.d.ts`):

| Key | Content |
|-----|---------|
| `control-tower.issues`, id `<issue>` | the full record |
| `control-tower.issueIds` | issue numbers of the project's records, sorted ascending |

`$.state` only offers `get` and `set`: the `issues` family cannot be listed and
an entry cannot be deleted. `issueIds` is therefore the list readers must use
to know which issues exist (the prompt banner, issue #7, and `/dash`,
issue #8, are meant to read it).

### `reloadIssues($, cwd)`

Called by the `classic.SessionStart` hook with the event's `cwd`. It never
rejects.

1. Finds `<project>` from `cwd` as for the store (main worktree basename).
2. Lists `$HOME/.claude/control-tower/<project>/`; only files named
   `<integer>.json` are records (temporary files, `notes.txt`, `abc.json` are
   ignored).
3. Reads and parses each record, in ascending order, and sets
   `issues[<issue>]` to its content.
4. Sets `issueIds` to the numbers of the records actually loaded.

Outcomes:

- missing directory: `issueIds` is `[]`, nothing logged;
- `cwd` outside a git repository: nothing written in `$.state`, nothing logged;
- unreadable record (invalid JSON or read error): skipped, absent from
  `issueIds`, its `issues` entry left unchanged, and
  `control-tower: read failed <project>/<issue>: <message>` logged; the other
  records still load;
- error on the directory (listing, `HOME` unset): nothing written in `$.state`
  and `control-tower: reload failed <project>: <message>` logged.

The hook then calls `next(e)`: the `SessionStart` result (e.g. the
`additionalContext` of another hook) is passed through unchanged, and a reload
failure never prevents the session from starting.

### Reload limits

- The records are read one after the other, before `next(e)`: the session start
  waits for the whole reload.
- A record deleted from disk leaves `issueIds` at the next reload, but its
  `issues` entry stays in `$.state` until the end of the session: only
  `issueIds` is authoritative.
- `saveIssue` adds to `issueIds` with a compare-and-set on the state version, so
  two saves of the same session do not drop a number; after 3 conflicting
  attempts it gives up silently, and the next `SessionStart` reload catches up.
- `classic.SessionStart` hooks do not run for a plugin installed by the user
  when an organization manages Claude Code (unless the plugin is listed in the
  managed settings): no reload happens there.
- `007.json` and `7.json` side by side give `7` twice in `issueIds`
  (issue #23).

### Notes

- Every `$.process.run` of the store has `timeoutMs: 1000`.
- Two sessions saving the same issue at once: no corrupted file thanks to `mv`,
  but the last write wins (no lock, no merge).
- The state contract has no `import` and uses the form
  `declare module 'claude-code' { interface PluginState { ... } }`;
  `claude plugin validate --strict control-tower` notes
  `declares state: control-tower.issues, control-tower.issueIds`.
- `validate` only reports the `$` calls written in `register.ts`; the store's
  calls are seen by `scripts/check-calls.sh` through the delegation object of
  `register.ts` (see [Constraints](#constraints)).

## Branch resolution

The tracked issue is read from the current branch name, never guessed: a branch
that does not match the pattern is not tracked.

### `branchPattern` option

Declared in `userConfig` of `control-tower/.claude-plugin/plugin.json`, shown in
`/config` as "Branch pattern". One value for all projects of the user (no
per-project setting). Default:

```
^(?:feat|fix|chore)/(\d+)-
```

Capture group 1 is the issue number: `feat/142-tva` gives 142, `feat/007-x`
gives 7, `feat/0-x` gives 0. With the default, the dash after the number is
required and `issue/…` is not recognised.

### `resolveIssue($, cwd, pattern)`

Returns `{ issue, branch, worktree }` or `null`. It never rejects and never
touches `$.state`.

1. Compiles `pattern` with `new RegExp`, before any git call.
2. Runs, in parallel and in `cwd`, each with `timeoutMs: 1000`:
   - `git branch --show-current` for `branch`;
   - `git rev-parse --show-toplevel` for `worktree` (absolute path).

   Only the trailing newline of their output is removed.
3. Matches `branch` against the pattern; `issue` is capture group 1 as a number.

Outcomes:

- branch not matched (e.g. `main`) or empty (detached HEAD): `null`, nothing
  logged;
- git failure (non-zero exit code, outside a repository) or rejected
  `$.process.run` (e.g. timeout): `null`, nothing logged;
- pattern that does not compile: `null` and
  `control-tower: invalid branchPattern <pattern>: <error message>`;
- branch matched but capture group 1 missing or not made of digits only:
  `null` and
  `control-tower: invalid branchPattern <pattern>: capture group 1 is not an issue number`.

Logs go to the transcript (`$.ui.log(..., { to: "transcript" })`). The empty
branch is checked before the pattern, so a detached HEAD never logs.

The `set_issue_step` hook passes the `branchPattern` value received in
`register(on, options)` and the cwd from `$.session.cwd()`.

## `set_issue_step` tool

Tool exposed to Claude as `mcp__control-tower__set_issue_step`, registered at
`session.start` with `isDeferred: false`. It moves the issue tracked on the
current branch (see [Branch resolution](#branch-resolution)) through the
workflow and records each accepted call in `history`. It needs no network.

### Input

| Field | Type | Rule |
|-------|------|------|
| `step` | required | one of `spec`, `tests-ecrits`, `tests-valides`, `vert`, `refacto`, `doc`, `mr`, `ci`, `termine`, or `bloque` |
| `note` | string | at most 200 characters, recorded in `history` |
| `title` | string | kept only when the issue has no title yet |
| `blockedReason` | string | required (non-empty) when `step` is `bloque`, ignored otherwise |

The engine does not check the input against the schema, so the hook does,
before resolving the issue (an invalid input is refused even on an untracked
branch). Only the length of `note` is checked, not the type of `note`, `title`
or `blockedReason`.

### Rules

Steps are ordered `spec → tests-ecrits → tests-valides → vert → refacto → doc →
mr → ci → termine`.

- An issue without a file stands before `spec`: only `spec` is accepted and
  creates the file (`branch` and `worktree` from the resolution, `title` from
  the input or `null`). The file and its directory are created by the call.
- Moving one step forward, staying on the current step or going back any number
  of steps is accepted. Skipping a step is refused, naming only the first
  missing step.
- `bloque` keeps `step` and sets `blockedReason`; it is refused like a skip when
  the issue has no file. On an already blocked issue it replaces the reason.
- Any real step clears `blockedReason` (unblocking), following the same
  transition rules.
- `branch` and `worktree` of an existing issue are kept.

Each accepted call appends `{ step, at, source: "claude", note }` to `history`,
`at` being `$.clock.now()` as ISO 8601:

- normal call: the given `note`, or `null`;
- `bloque`: the current step, with `blockedReason` as `note` (the given `note`
  is ignored);
- unblocking: `note` is `"unblocked"`, or `"unblocked; <note>"` when a note is
  given.

### Answers

Every answer is a tool result (`{ result }`) sent to Claude, in English:

| Case | Answer | File |
|------|--------|------|
| invalid `step` | ``Invalid step `<step>`. Expected one of: `spec`, `tests-ecrits`, `tests-valides`, `vert`, `refacto`, `doc`, `mr`, `ci`, `termine`, `bloque`.`` | unchanged |
| `note` too long | `` `note` must be at most 200 characters.`` | unchanged |
| `bloque` without reason | `` `blockedReason` is required when step is `bloque`.`` | unchanged |
| untracked branch, invalid `branchPattern` | `No issue tracked on this branch. Do not retry; ask the user to switch to an issue branch.` | none |
| unreadable file (`loadIssue` gives `'unreadable'`) | `Failed to read issue <n>; see the transcript.` | unchanged |
| skipped step | ``Missing intermediate step: `<step>`. Move to `<step>` first.`` | unchanged |
| `saveIssue` returns `false` | `Failed to save issue <n>; see the transcript.` | see [`saveIssue`](#saveissue-record) |
| step accepted | ``Issue <n> moved to `<step>`.`` | written |
| `bloque` accepted | `Issue <n> blocked: <blockedReason>.` | written |

Details of read and save failures go to the transcript (see
[Issue store](#issue-store)).

### Permission

The `tool.call` hook answers without calling `next(e)`: the call never reaches
the core, so no permission dialog is shown. `validate` notes this gating hook
has no `.catch`.

## Automatic transitions

The mod observes every Bash command Claude runs and moves the tracked issue
forward or back by itself in four mechanical cases. The observation never
changes the command: Claude always receives the Bash result unchanged, even
when the observer fails.

### Rules

| Command (exit code) | From step | To step |
|---------------------|-----------|---------|
| test run (see [`testPattern`](#testpattern-option)), code 0 | `tests-valides` only | `vert` |
| test run, code not 0 | `vert`, `refacto`, `doc`, `mr`, `ci` | `tests-valides` |
| `gh pr create` or `glab mr create`, code 0 | any step before `mr` | `mr` |
| `git worktree remove <path>`, code 0, on the worktree of a tracked issue | any step but `termine` | `termine` |

In every other case the issue is left unchanged: a test run failing in
`tests-ecrits` is the normal red phase, tests passing in `tests-ecrits` or
`refacto` change nothing, a PR created at `ci` does not go back to `mr`, a
failed command moves nothing. The automatism never moves an issue forward to
`tests-valides`, nor to `spec`, `tests-ecrits`, `refacto`, `doc` or `ci`: those
remain Claude's (via [`set_issue_step`](#set_issue_step-tool)).

When one command matches several rules (e.g. `make test && gh pr create`), only
the most advanced target applies: `termine` > `mr` > tests. A
`git worktree remove` command is never checked against the test and PR rules.

Each automatic move appends `{ step, at, source: "auto", note }` to `history`,
`note` being the command cut to its first 200 characters. A blocked issue moves
like any other and stays blocked (`blockedReason` is kept).

### Recognition

A rule only matches a command actually run: at the start of the command, or
after `&&`, `;` or `|`. A mere mention (`grep -n "gh pr create" NOTES.md`,
`cat phpunit.xml`, `ls vendor/bin/phpunit`,
`git worktree list && echo git worktree remove /w/x`) is not recognised.
`gh pr create` is recognised even when `gh` is a shell function.

### Which issue

- Tests and PR/MR: the issue tracked on the branch of the session cwd (see
  [Branch resolution](#branch-resolution)), or of `<path>` when the command
  starts with `cd <path> &&`.
- `git worktree remove <path>`: the issue tracked on the branch of `<path>`
  (first argument that is not a flag), resolved and loaded **before** the
  command runs, while the worktree still exists. After the removal the record is
  saved through the main worktree (noted before removal), so it works even when
  the session itself was opened in the removed worktree.

### Ignored commands

Nothing happens (no file created or changed, nothing logged) when:

- the branch is not tracked, or the issue has no file yet (only `spec`, through
  `set_issue_step`, creates it);
- the file is unreadable (only the `read failed` line of
  [`loadIssue`](#loadissue-worktree-issue) is logged);
- the command runs in the background or is interrupted;
- the command did not run to its end: killed by the Bash timeout (code 143,
  `Command timed out`), or refused by a permission rule or by the auto mode
  classifier. Technically, an error result counts as a failure only when its
  text starts with `Exit code N` and does not contain `Command timed out`;
- no rule applies to the current step (see the table above).

A command matching no rule makes no git call and no store access.

### `testPattern` option

Declared in `userConfig` of `control-tower/.claude-plugin/plugin.json`, shown in
`/config` as "Test pattern". A regex searched in the Bash command; one value for
all projects of the user. Default:

```
(^|[;&|]\s*)(docker compose exec \S+ )?(\S*/)?(phpunit|pest|pytest)(\s|$)|(^|[;&|]\s*)make test\b
```

It recognises `phpunit`, `pest`, `pytest` (bare or with a path, e.g.
`vendor/bin/phpunit`), optionally behind `docker compose exec <service>`, and
`make test`, at the start of the command or after `&&`, `;` or `|`. A custom
value replaces the default (e.g. `\bnpm test\b` recognises `npm test` and no
longer `phpunit`).

A pattern that does not compile disables the test rules only (the PR/MR and
worktree rules stay active) and logs, on each observed Bash command:

```
control-tower: invalid testPattern <pattern>: <error message>
```

PR/MR recognition is not configurable.

### Sub-agents

Bash commands run by a sub-agent are observed like those of the session. The
issue is resolved from the cwd of the main session, or from a leading
`cd <path> &&`; the sub-agent's own cwd is not followed.

### Limits

- A pipeline reports the exit code of its last command: `phpunit | tee log`
  counts as a success when `tee` succeeds.
- A test command that is not found (code 127) counts as a failed test run
  (issue #19).
- Not recognised by default: `docker exec …`, `env X=1 phpunit`,
  `env X=1 gh pr create`, `command gh pr create`, paths with spaces (in
  `cd <path> &&` and `git worktree remove`), a relative path after `cd` for
  `git worktree remove` (issue #21).
- Text quoted after a separator is taken for a command
  (`echo "x && gh pr create"`, issue #20).
- The refusal by the auto mode classifier is ignored through the general rule
  above (no `Exit code N`), not checked against a real refusal.
- Every process the observer starts has a 1 s timeout; on a tracked issue the
  added delay is about 4 s in the worst case, and none for a command that
  matches no rule.
- The invalid `testPattern` log is repeated on each Bash command (issue #18).

## Constraints

The engine refuses to pass `$` to an imported function. `register.ts`
therefore gives `resolveIssue`, `loadIssue`, `saveIssue` and `reloadIssues` a
delegation object (built by `closures($)`, shared by the hooks) whose closures
call `$` only for the calls these helpers make. Some calls need literal
arguments to pass `validate`: `env.get` always reads `HOME`, `state.get` always
reads `control-tower.issueIds`, and `state.set` writes `control-tower.issueIds`
when the caller's key is `issueIds`, otherwise `control-tower.issues` (only
`id` comes from the caller). A new `$` call in a helper must be added to this object.


Mod code uses no `setTimeout`, `fetch` or Node API: only `$.clock`, `$.fs`,
`$.process` (and the other allowed `$` nouns). The types generated in
`control-tower/.claude-plugin/types/` are the reference. This rule is not
checked automatically beyond `scripts/check-calls.sh`.
